# Функционал: Уточняющий диалог перед RAG-поиском

## Суть идеи

Вместо немедленного поиска по первому сообщению пользователя — бот сначала собирает контекст через 2–3 уточняющих вопроса, затем делает более точный поиск с обогащённым запросом.

---

## Фаза 1 — Классификация намерения

После первого сообщения LLM анализирует его по двум критериям:

**Нужны ли уточнения?**
- Запрос конкретный и самодостаточный → немедленный поиск (как сейчас)
- Запрос расплывчатый или многозначный → переход к уточняющему диалогу

**Примеры:**
- *«Какой штраф за академическую задолженность?»* → конкретно → поиск сразу
- *«Что мне делать?»* / *«Расскажи про правила»* → расплывчато → уточнения
- *«Какие есть льготы?»* → многозначно (стипендия? общежитие? питание?) → уточнения

---

## Фаза 2 — Серия уточняющих вопросов

Бот задаёт **не более 3 вопросов**, по одному за раз.

### Откуда берутся вопросы

LLM генерирует их динамически, опираясь на:
- исходный запрос пользователя
- список доступных документов из метаданных Qdrant (`doc_title`, `section_title`)
- уже полученные ответы в текущем диалоге

### Типы уточнений

| Тип | Пример вопроса |
|---|---|
| Уточнение темы | *«Вас интересует академическая сторона вопроса или административная?»* |
| Уточнение статуса | *«Вы бакалавр или магистрант?»* |
| Уточнение контекста | *«Это касается текущего семестра или прошлого?»* |
| Уточнение документа | *«Вас интересует устав университета или правила внутреннего распорядка?»* |

### Формат ответа

Где возможно — **кнопки с вариантами** (inline keyboard), где нет — свободный текст. Это снижает нагрузку на пользователя и ускоряет диалог.

### Остановка диалога

Уточнения прекращаются если:
- Получено 3 ответа
- LLM решил, что контекста уже достаточно
- Пользователь написал *«не знаю»* / *«неважно»* / отправил `/skip`

---

## Фаза 3 — Обогащение запроса

После сбора уточнений формируется **расширенный запрос** для поиска.

### Что входит в обогащённый запрос

```
Оригинальный запрос:    «Какие есть льготы?»
Уточнения:              статус=бакалавр, тема=общежитие, период=текущий год
Расширенный запрос:     «льготы на проживание в общежитии для студентов 
                         бакалавриата 2024-2025»
```

Помимо текстового расширения, формируется **профиль поиска** — структурированный объект, который передаётся в Retriever:

- `topics` — ключевые темы
- `user_type` — статус пользователя (бакалавр / магистр / сотрудник)
- `document_hints` — предпочтительные документы если пользователь уточнил
- `temporal_context` — временной контекст если упомянут

---

## Фаза 4 — Умный выбор чанка

Это ключевое изменение в Retriever. Вместо одного критерия (cosine similarity) — **многофакторная оценка**.

### Факторы ранжирования

| Фактор | Вес | Описание |
|---|---|---|
| Семантическое сходство | 35% | Cosine similarity с обогащённым запросом (как сейчас) |
| Соответствие типу пользователя | 20% | Чанк упоминает «бакалавр» если пользователь — бакалавр |
| Соответствие документу | 15% | Совпадение с `document_hints` из профиля |
| Позиция в документе | 10% | Заголовки разделов и начало документа весят больше |
| Временная актуальность | 10% | Более свежие документы приоритетнее при прочих равных |
| Семантика заголовка раздела | 10% | Сходство `section_title` с темой запроса отдельно от тела чанка |

### LLM-реранкинг финального набора

После числового скоринга — финальная выдача (топ-10 кандидатов) передаётся LLM-реранкеру, который выбирает топ-5 с объяснением почему каждый чанк релевантен или нет. Это отсеивает ложные совпадения по похожим словам при разном смысле.

## Новые состояния FSM

```
[Верифицирован]
      │
      ▼
QueryReceived
      │
      ├── запрос конкретный ──────────────────► RAGSearch (как сейчас)
      │
      └── запрос расплывчатый
                │
                ▼
         Clarification_1
                │
                ▼
         Clarification_2  (если нужно)
                │
                ▼
         Clarification_3  (если нужно)
                │
                ▼
         EnrichQuery → RAGSearch (улучшенный)
```

---

## Логирование

В таблицу `query_logs` добавляются поля:
- `clarification_rounds` — сколько уточнений было задано
- `enriched_query` — итоговый обогащённый запрос
- `user_profile` — JSON-профиль пользователя из уточнений
- `reranker_scores` — финальные скоры всех факторов по выбранным чанкам

Это даст администратору понимание: где бот часто уточняет (значит документы плохо структурированы или запросы типично расплывчатые), и где реранкинг кардинально меняет порядок чанков относительно чистого cosine similarity.

---

## Что это даёт

- Точность поиска растёт за счёт того, что запрос несёт больше смысловой нагрузки
- Уменьшается число ответов вида «не нашёл информации» по расплывчатым запросам
- Многофакторный скоринг убирает ситуации когда «правильный» чанк стоит на 6–7 месте из-за чуть меньшего cosine score
- Логи уточнений помогают понять какие темы вызывают затруднения у студентов
