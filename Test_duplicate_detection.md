# Тест-план: система выявления дубликатов и устаревших данных

**Базовый документ:** `1.pdf` — ДП-AITU-19 «Методические указания к выполнению магистерских диссертаций» (Редакция 1, 2023)

---

## Тестовые файлы

| Файл | Ожидаемый результат | Целевое сходство |
|------|--------------------|--------------------|
| `test_duplicate.pdf` | ⚠️ DUPLICATE | cosine ≥ 0.90 |
| `test_stale.pdf` | ⚠️ STALE (LLM подтверждает) | cosine 0.75–0.90 |
| `test_unrelated.pdf` | ✅ Нет предупреждений | cosine < 0.75 |

## Сценарий 1 — DUPLICATE (`test_duplicate.pdf`)

### Что это
Прямая русскоязычная копия `1.pdf`: тот же документ ДП-AITU-19, те же разделы, те же формулировки на русском языке, та же структура и нумерация — только другое имя файла. Смысловое содержание идентично оригиналу.

### Почему должен сработать как DUPLICATE
Embedding-модель работает семантически: «Магистерская диссертация является завершающим этапом» в обоих файлах даст практически идентичные векторы. Структура, терминология, нумерация разделов — всё совпадает. Это наиболее «чистый» тест порога 0.90.

### Ожидаемое поведение системы
- cosine similarity ≥ 0.90 между чанками из `test_duplicate.pdf` и `1.pdf`
- Флаг **DUPLICATE** без обращения к LLM
- Telegram-уведомление администратору с % сходства и совпадающим фрагментом

### Команды для проверки
```
/warnings         — должна появиться запись DUPLICATE
/history test_duplicate.pdf  — должна появиться запись о загрузке
/resolve <id>     — закрыть после проверки
```

### Возможные ошибки, которые обнаружит этот тест
- Порог 0.90 слишком высок и копия не попадает в DUPLICATE даже при идентичном тексте → критический баг в конфигурации порогов
- Функция исключения «файлы с тем же именем» не работает в обратную сторону: имя другое, но контент тот же — система должна корректно найти пару
- Дедупликация предупреждений: если у документа 20 чанков-дублей, должно быть 1 предупреждение, не 20

## Сценарий 2 — STALE (`test_stale.pdf`)

### Что это
«Редакция 2» того же регламента ДП-AITU-19, датированная 2024 годом. Структура и тема идентичны, но внесены значимые изменения:
- Объёмы работ увеличены (50–60 стр. → 60–80 стр.)
- Добавлено требование ИИ-декларации
- Число обязательных публикаций: 1 → 2
- Новые правила оформления (шаблон v2.0, PlantUML, minted)
- Обновлены требования к руководителю
- Новые сроки и форматы подачи документов

### Почему должен сработать как STALE
Достаточно похож (же тема, те же разделы), чтобы попасть в зону 0.75–0.90. Достаточно отличается (новые требования, другие числа, новые разделы), чтобы LLM отличил «обновлённая версия» от «дубликат».

### Ожидаемое поведение системы
- cosine similarity 0.75–0.90 → передаётся Groq LLM
- LLM возвращает **STALE** с причиной типа: "New document appears to be Revision 2 of the same regulation, containing updated volume requirements and new AI declaration rules"
- Telegram-уведомление с причиной от LLM

### Команды для проверки
```
/warnings         — запись STALE с причиной LLM
/history 1.pdf    — должна показать 1.pdf как "возможно устаревший"
/resolve <id>     — после ручной проверки (например, удалить 1.pdf через /delete)
```

### Возможные ошибки, которые обнаружит этот тест
- LLM классифицирует как DUPLICATE вместо STALE → промпт для LLM недостаточно чёткий
- LLM не видит разницы и возвращает «просто похожая тема» → нужно передавать больше контекста чанков
- Причина от LLM на английском, хотя документы на русском → проверить язык ответа LLM
- Поле причины пустое в /warnings → баг сохранения LLM-ответа в SQLite

## Сценарий 3 — UNRELATED (`test_unrelated.pdf`)

### Что это
Документ ДП-AITU-33 «Политика информационной безопасности» — тот же университет, но совершенно другая тема: пароли, VPN, MDM, персональные данные, инциденты ИБ.

### Почему НЕ должен сработать
Семантически далёк от методических указаний по диссертациям. cosine similarity должен быть < 0.75 со всеми чанками из `1.pdf`.

### Ожидаемое поведение системы
- Ни одно предупреждение не создаётся
- Документ индексируется в Qdrant нормально
- Уведомление в Telegram НЕ отправляется
- В `/warnings` ничего нового нет

### Возможные ошибки, которые обнаружит этот тест
- Ложное срабатывание DUPLICATE/STALE → порог слишком низкий или embedding-модель даёт высокое сходство для текстов одного домена (AITU)
- Сбой загрузки при отсутствии предупреждений → ошибка в ветке «warnings пустой»
- Telegram-уведомление всё равно отправляется (баг в условии `if warnings`)

## Дополнительные граничные тесты

### Тест 4 — Повторная загрузка того же файла
**Действие:** Загрузить `1.pdf` повторно под тем же именем.  
**Ожидание:** Система должна исключить файл с тем же именем из сравнения (параметр "исключая файлы с тем же именем"). Предупреждений быть не должно.  
**Риск:** Если исключение не работает, документ сравнивается сам с собой → ложный DUPLICATE.

### Тест 5 — Сбой LLM
**Действие:** Загрузить `test_stale.pdf` при недоступном Groq API (временно передать неверный ключ).  
**Ожидание:** Загрузка должна завершиться успешно. Чанки с similarity 0.75–0.90 либо игнорируются, либо помечаются как STALE с причиной "LLM unavailable".  
**Риск:** Сбой LLM блокирует загрузку документа.

### Тест 6 — Дедупликация предупреждений
**Действие:** Загрузить `test_duplicate.pdf` (много чанков совпадут с `1.pdf`).  
**Ожидание:** В SQLite и в `/warnings` — максимум 1 запись для пары (test_duplicate.pdf, 1.pdf).  
**Риск:** N записей на N совпадающих чанков → спам в Telegram и захламление таблицы.
