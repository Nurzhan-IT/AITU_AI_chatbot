# Улучшение пайплайна классификации `needs_clarification`

Документ описывает слабые места текущей реализации классификатора намерения
и уточняющего диалога, и предлагает варианты улучшений — от точечных
исправлений (1–2 часа работы) до архитектурного рефакторинга (1–2 недели).
Контекст: корпус 70–120 документов, около 1–10k чанков в Qdrant.

---

## 1. Диагностика текущего пайплайна

### 1.1. Что делает классификатор сейчас

[rag/dialog/classifier.py:28](rag/dialog/classifier.py#L28) — один LLM-вызов:
- видит **только текст вопроса**;
- не знает про корпус (какие документы вообще проиндексированы);
- не знает про историю предыдущих диалогов с этим пользователем;
- возвращает бинарное `True/False` без confidence;
- `temperature=0`, `max_tokens=1000` (избыточно — JSON ~50 токенов);
- на ошибку → fallback `False` (деградация в текущий поиск).

### 1.2. Узкие места

| # | Проблема | Последствие |
|---|----------|-------------|
| 1 | **Корпус-незнание.** LLM решает «нужно уточнение» абстрактно, без учёта того, что лежит в Qdrant. | Конкретный вопрос про несуществующий в корпусе документ → классифицируется как `specific`, поиск возвращает шум, юзер получает «не знаю». Размытый вопрос про единственный имеющийся документ → запускается лишний диалог. |
| 2 | **Бинарный выход.** Нет понятия «пограничный случай». | Запросы с similarity 0.4–0.6 (low confidence retrieval) уходят либо в прямой ответ, либо в диалог без обоснования. |
| 3 | **Нет retrieval-сигнала.** Не используется тот факт, что Qdrant уже умеет давать distribution score-ов. | Самый сильный сигнал «ambiguous» — это когда top-K чанков рассыпан по разным документам с близкими score-ами. Этот сигнал не задействован. |
| 4 | **Игнорируется контекст диалога.** Каждый текст идёт через классификатор «с нуля». | После завершённого уточнения, follow-up вопрос «А для магистрантов?» — снова классифицируется как `vague_topic` и снова запускает диалог. |
| 5 | **Промпт статический.** Не содержит ни одного примера из реального корпуса AITU. | Few-shot подсказки оторваны от домена. |
| 6 | **Нет метрик качества.** Нет labeled dataset, нет регрессионного теста. | Невозможно сказать, ухудшил ли свежий правки промпта качество. |
| 7 | **5+ LLM-вызовов на один уточнённый запрос.** classify → next_clarification × N → enrich + profile → rerank → generate. | Латентность 8–15 секунд, существенные затраты на API. |
| 8 | **`enrich_query` и `extract_profile` дублируются.** Оба видят `original + answers` и параллельно гоняют LLM. | Лишний вызов — можно объединить в один. |
| 9 | **`profile_has_signal` — простой OR.** Любой непустой слот включает `search_with_profile + LLM rerank`. | Дорогой путь триггерится даже при слабом сигнале. |
| 10 | **Кэш `_get_cached_docs` глобальный с TTL 10 мин.** Не инвалидируется при upload документа. | До 10 минут после загрузки нового документа LLM-генератор уточняющих вопросов «не видит» новое название. |
| 11 | **Стоп-слова hardcoded RU/EN.** | KZ-пользователю надо знать `/skip` или нажимать кнопку. |

## 2. Quick wins (низкий риск, 1–4 часа на каждый)

### 2.1. Сократить `max_tokens` классификатора до 50
[rag/dialog/classifier.py:38](rag/dialog/classifier.py#L38). Ответ — однострочный JSON, тратить
1000 токенов на буфер бессмысленно. Экономит latency и стоимость.

### 2.2. Добавить `confidence` в выход классификатора
Промпт уже выводит `reason`. Добавить:
```json
{"needs_clarification": true, "reason": "ambiguous", "confidence": 0.0–1.0}
```
Использовать threshold: `>= 0.7` → диалог, `0.4–0.7` → пограничный (см. п. 3.2),
`< 0.4` → прямой поиск.

Оговорка: self-reported confidence от LLM при `temperature=0` калибруется
плохо — это эвристика, а не вероятность. §2.2 — временная мера: статистический
триаж по распределению score (§3.3) даёт честный сигнал «пограничности» и по
сути вытесняет это поле. Не вкладываться в тонкую настройку порогов confidence.

### 2.3. Skip-слова на KZ
[bot/handlers/dialog.py:32](bot/handlers/dialog.py#L32) — добавить `"білмеймін"`, `"маңызды емес"`, `"өткізіп жіберу"`.

### 2.4. Инвалидация doc-кэша при upload
Кэш `_docs_cache` определён в [rag/dialog/question_gen.py](rag/dialog/question_gen.py),
а не в ingest. Добавить туда публичную функцию `invalidate_docs_cache()`
(сброс `expires_at = 0`) и вызывать её из [ingestion/ingest.py](ingestion/ingest.py)
после успешной загрузки. Импорт по месту, чтобы не плодить циклы. Мутировать
приватный `_docs_cache` снаружи модуля не нужно.

### 2.5. Объединить `enrich_query` + `extract_profile` в один LLM-вызов
[rag/dialog/enricher.py](rag/dialog/enricher.py) — обе функции читают один и
тот же вход (`original + answers`) и гоняют LLM параллельно. Можно одним
вызовом получить `{enriched: "...", profile: {...}}`. Нюанс реализации:
`extract_profile` возвращает JSON, а `enrich_query` — чистый текст (промпт
требует «Output PLAIN TEXT only»). Объединённый вызов переводит вывод enrich
в JSON — учесть это в парсинге и в ветке fallback. Экономит ~1 секунду на
диалог.

### 2.6. Расширить few-shot примеры доменными
В [rag/dialog/prompts.py:28–35](rag/dialog/prompts.py#L28-L35) добавить 4–6 примеров
ИЗ КОРПУСА AITU: реальные названия документов, реальные user-type-зависимые
вопросы. Это даёт ощутимый прирост точности на узкой доменной модели.

### 2.7. Логировать `classification_reason` в `query_logs`
Работа в трёх местах: (1) колонку добавить в схему `query_logs` —
[duplicate_detection/db.py](duplicate_detection/db.py), там же есть готовый
идемпотентный паттерн миграции `ALTER TABLE … except OperationalError`;
(2) параметр добавить в `log_query` и в `INSERT` —
[bot/handlers/feedback.py](bot/handlers/feedback.py); (3) значение `reason`
протащить из `classify_intent` в [bot/handlers/user.py](bot/handlers/user.py)
до вызова `log_query`, а для уточнённых запросов — ещё и через FSM-состояние
(в `_proceed_to_search` исходный `intent` сейчас недоступен). Нужно для
построения evaluation set из реальных запросов.

## 3. Корпус-ориентированная классификация (основной рефакторинг)

### 3.1. Идея пользователя — расширенная

Текущая идея: получить чанки с similarity > 70%, скормить их саммари в LLM,
сгенерировать N уточняющих вопросов, после ответов отсеять чанки/документы,
сгенерировать финальный ответ.

Это известная техника — **retrieval-grounded clarification**. Она даёт
несколько важных свойств бесплатно:

- Уточняющий вопрос гарантированно про то, что есть в корпусе (LLM не выдумает
  «бакалавр или магистрант?», если у вас все документы для одной аудитории).
- Решение «нужно ли уточнять» становится не семантическим, а статистическим:
  смотрим на распределение score-ов реального поиска.
- Если корпус по теме отсутствует совсем — можно сразу честно сказать
  «нет данных», не гоняя диалог впустую.

### 3.2. Предлагаемый пайплайн

```
┌──────────────────────────────────────────────────────────────────┐
│ User Query                                                       │
│   ↓                                                              │
│ Stage 1: Cheap heuristics  (без LLM)                             │
│   - length < 2 слов?                                             │
│   - содержит только стоп-слова?                                  │
│   → если да: needs_clarification = True (reason="too_short")     │
│   → иначе: продолжаем                                            │
│                                                                  │
│ Stage 2: Probe retrieval  (один Qdrant вызов, top-15)            │
│   - embed(query) → search(k=15)                                  │
│   - анализируем score distribution                               │
│                                                                  │
│ Stage 3: Triage по сигналам поиска  (без LLM)                    │
│   ┌─────────────────────────────────────────────────────────┐    │
│   │ A. Top score < 0.50           → out_of_scope            │    │
│   │ B. Top1 > 0.80 AND gap > 0.15 → SPECIFIC: прямой ответ  │    │
│   │ C. Top-5 средн. > 0.70 AND    → AMBIGUOUS: уточнение,   │    │
│   │    распределены по ≥3 docs       grounded в этих docs   │    │
│   │ D. Все остальные              → передать в LLM classifier│    │
│   └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│ Stage 4: LLM verdict  (только для пограничных)                   │
│   - в промпт уже входят doc_titles + section_titles top-5        │
│   - LLM решает: уточнять или нет, с привязкой к найденному       │
│                                                                  │
│ Stage 5: Grounded clarification  (если нужно)                    │
│   - в next_clarification передаётся top-15 (а не весь корпус)    │
│   - LLM выбирает варианты ИЗ ЭТИХ документов                     │
│                                                                  │
│ Stage 6: Filter & re-retrieve                                    │
│   - после ответов фильтруем top-15 по: doc_title, section_title, │
│     user_type keyword, document_hints                            │
│   - если фильтр оставил < top_k → дополняем новым поиском с      │
│     enriched query                                               │
│                                                                  │
│ Stage 7: Generate                                                │
└──────────────────────────────────────────────────────────────────┘
```

> **Замечания к схеме.**
> - *Stage 1:* порог по длине намеренно строгий — только запрос из одного
>   слова. «length < 3» ловил бы двухсловные именные группы («академический
>   отпуск», «стоимость пересдачи»), которые как раз наиболее
>   поисковопригодны; короткий запрос ≠ размытый.
> - *Stage 3:* числовые пороги в блоке A/B/C — иллюстрация формы правил, а не
>   рабочие дефолты. Реальные значения зависят от эмбеддера — см. §3.3.

### 3.3. Триаж по score distribution

⚠️ **Дефолтные пороги нельзя брать с потолка — они зависят от эмбеддера.**
Эмбеддер проекта — `intfloat/multilingual-e5-large` (cosine, L2-нормализация,
префиксы `query:`/`passage:`). e5-модели дают **сжатое распределение косинуса
в узкой полосе ≈0.70–0.92**: даже нерелевантный чанк редко падает ниже 0.70,
а разрыв top1–top2 в 0.15 почти не встречается.

Поэтому абсолютные пороги ниже — это НЕ рабочий бейзлайн, а иллюстрация формы
правил. С наивными числами на e5:

```python
# ИЛЛЮСТРАТИВНО — НЕ использовать как дефолты на e5!
TRIAGE_TOP1_HIGH        = 0.80   # на e5 top1 > 0.80 почти всегда → rule B не отсекает
TRIAGE_GAP_TO_NEXT      = 0.15   # на e5 gap > 0.15 почти не бывает → rule B мёртв
TRIAGE_TOP5_AMBIG_MEAN  = 0.70   # на e5 top5 mean > 0.70 почти всегда → rule C переусердствует
TRIAGE_TOP5_DOC_SPREAD  = 3      # ≥3 разных документа в top-5
TRIAGE_OUT_OF_SCOPE     = 0.50   # на e5 top1 < 0.50 не бывает → rule A мёртв
```

С этими числами rule A и B не срабатывают никогда, а rule C вырождается в
«≥3 документа» и запускает диалог почти на каждый запрос.

**Что делать вместо этого:**

1. **Сначала измерить, потом задавать пороги.** В фазе B (§5) снять
   распределение `top1`, `gap`, `top-K mean` на ≥200 реальных запросах и взять
   пороги из перцентилей, а не из round-чисел. Без этого Stage 3 запускать
   нельзя.
2. **Предпочесть масштабонезависимые признаки** абсолютным порогам — они
   переживают смену эмбеддера и корпуса:
   - `gap` как отношение `(top1 - top2) / std(top-K)` или z-score, а не
     абсолютные 0.15;
   - нормированная энтропия распределения score top-K как мера «размазанности»;
   - перцентильный ранг top1 относительно истории запросов.
3. **Согласовать с конфигом.** В [config.py](config.py) уже есть
   `min_chunk_score = 0.55` — текущий «шумовой пол». Порог out_of_scope должен
   опираться на него, а не вводить параллельную константу 0.50.

§3.5 R2 (вынос порогов в config + регенерация) остаётся в силе как дополнение
к пунктам 1–2, а не как замена им.

### 3.4. Зачем это лучше текущей реализации

| Аспект | Сейчас | После |
|--------|--------|-------|
| Корпус-привязка решения | нет | да (через score distribution) |
| Кол-во LLM-вызовов на быстрый путь | 1 (classifier) + 1 (generate) | 0 (classifier) + 1 (generate) |
| Кол-во LLM-вызовов на диалог | 1 + N(1–3) + 2 + 1 + 1 = 6–8 | 0–1 + N(1–3) + 1 + 1 = 3–6 |
| Качество уточняющих вопросов | LLM видит весь корпус, может выбрать нерелевантную ось | LLM видит только top-15 — оси привязаны к данным |
| Out-of-scope detection | нет | да (по калиброванному порогу, §3.3) |
| Latency p50 | 8–15 c | 4–8 c |

### 3.5. Риски и как их закрыть

- **R1: ложный «прямой ответ» по top1 > 0.80.**  
  Cosine similarity 0.85 ≠ «семантически тот же вопрос». Mitigation: добавить
  LLM-reranker верификацию ТОЛЬКО на этом одном чанке (cheap), либо отлавливать
  на этапе генерации через явный «I don't know» промпт.

- **R2: пороги триажа дрейфуют при смене эмбеддера/корпуса.**  
  Mitigation: вынести в `config.py`, добавить периодическую регенерацию из
  labeled set.

- **R3: probe retrieval тратит время даже при тривиальных запросах.**  
  Сам Qdrant-поиск top-15 на 1–10k чанках — единицы миллисекунд. Реальная
  стоимость — `embed(query)`: сетевой вызов к OpenRouter, ~150–400 мс.
  Mitigation: переиспользовать probe-вектор для финального поиска (Stage 6) —
  тогда probe не добавляет embed-вызов, а перемещает уже существующий.

## 4. Дополнительные улучшения

### 4.1. Conversation-aware classification

Хранить последний завершённый `original_query` и `profile` пользователя в FSM
короткий TTL (например, 5 мин). При новом сообщении сначала спросить у LLM:
```
[last_turn_context]
[new_message]
Это follow-up предыдущего вопроса (использовать тот же профиль)
или новый вопрос (классифицировать заново)?
```
Решает кейс «А для магистрантов?» после уточнённого диалога.

### 4.2. Hybrid retrieval как альтернатива переуточнению

Часть «vague» запросов лучше решается не диалогом, а **BM25 + dense fusion**.
Например, «правила» — это keyword-match задача, embedding модель тут проигрывает.
Qdrant поддерживает sparse + dense гибрид. На корпусе 70–120 документов
это даст +5–10% recall@5 практически бесплатно.

### 4.3. Кэш классификатора

Hash вопроса → результат на 24 часа. На корпусе FAQ-подобных запросов
дубликаты неизбежны.

### 4.4. Структурированный output вместо JSON parsing

Многие LLM-провайдеры поддерживают `response_format={"type": "json_schema", ...}`.
Если Groq/OpenRouter модель поддерживает — заменить «найти первый {» на строгий
schema. Уберёт класс ошибок «модель завернула JSON в markdown».

### 4.5. Telemetry → curated dataset

Добавить в feedback flow столбец `was_clarification_helpful`. Через 1–2 недели
получится 200–500 размеченных кейсов — на них можно:
- замерить precision/recall классификатора;
- сделать прогон A/B новых промптов;
- понять реальное распределение `reason` (`vague_topic` vs `ambiguous`).

### 4.6. Адаптивное число раундов

Сейчас жёсткий лимит 3. Можно сделать: если после первого ответа
profile_has_signal становится «сильным» (≥ 2 непустых слота) → один раунд
достаточно. Сокращает диалог в большинстве случаев.

### 4.7. Кэш doc-summary

При корпусе 70–120 документов имеет смысл предкэшировать **краткое описание
каждого документа** (1–2 предложения). Поместить в payload Qdrant или
отдельную SQLite-таблицу. Использовать в `next_clarification` как
input — даст более осмысленные варианты выбора.

### 4.8. Закрыть тихие пути в классификаторе

В [rag/dialog/classifier.py](rag/dialog/classifier.py) под «удалить избыточный
fallback» смешаны две разные ситуации:

- **Строка 51** (`reason = "vague_topic" if needs else "specific"`) — это НЕ
  маскировка ошибки парсинга. JSON к этому моменту уже распарсился, а
  `needs_clarification` прочитан. Строка срабатывает, только когда модель
  вернула `reason` вне валидного множества. Вывести `reason` из валидного
  `needs` здесь корректно — трогать не обязательно.
- **Строка 48** (`needs = bool(data.get("needs_clarification"))`) — вот
  настоящая тихая дыра: если ключа нет, `bool(None) = False`, и ответ
  бесшумно превращается в «уточнение не нужно». Отсутствие ключа должно явно
  падать в `ValueError` → fallback на правилах (§3.2 stage 1/3), а не молча
  становиться `False`.
- **Строка 53** — реальные ошибки парсинга `except` уже ловит корректно и
  возвращает `reason="error"`. Это поведение менять не нужно.

Зависимость: «fallback на правилах» существует только после §3.2. До этого
момента §4.8 сводится к замене молчаливого `False` на явный `raise`.

### 4.9. Порог силы профиля для дорогого пути

[bot/handlers/dialog.py:158](bot/handlers/dialog.py#L158) — `profile_has_signal`
сейчас простой OR: любой один непустой слот включает `search_with_profile +
LLM rerank`. Заменить на оценку силы: дорогой путь только при ≥2 непустых
слотах ИЛИ при наличии «сильного» слота (`user_type` / `document_hints`).
Один слабый `topics` из одного слова не должен триггерить реранкер. Закрывает
узкое место №9.

## 6. Конкретный пример: что произойдёт при «Расскажи про правила»

### Сейчас
```
classify_intent("Расскажи про правила")
  → LLM: {"needs_clarification": true, "reason": "vague_topic"}    [~800ms]
next_clarification(state, ALL_DOCS_TITLES)
  → LLM: {"question": "Какие правила вас интересуют?",
          "options": ["Академические", "Общежитие", "Финансовые", "Другое"]}
  → LLM выбирает оси абстрактно, может промахнуться мимо реального покрытия [~1500ms]
…N раундов…
enrich_query + extract_profile (параллельно)                       [~1500ms]
search_with_profile + rerank_chunks                                [~2000ms]
generate                                                           [~2500ms]
Итого: 10–13 секунд
```

### После рефакторинга
```
probe_retrieval("Расскажи про правила")                  [~300ms: embed+Qdrant]
  → top-15: 7 чанков из "правил_общежития.pdf", 5 из "академ_политика.pdf",
    3 из "финансовый_регламент.pdf"
triage(scores, doc_spread)
  → "ambiguous": top5 mean 0.74, 3 разных документа → нужен диалог
next_clarification(query, top15_docs)
  → LLM видит 3 конкретных документа, варианты:
    ["Правила проживания в общежитии", "Академическая политика",
     "Финансовый регламент"]                                       [~1000ms]
User: "Общежитие"
filter_chunks(top15, doc_hint="общежитие")
  → 7 чанков остались, embed не нужен
generate(original_query, filtered_chunks)                          [~2500ms]
Итого: 4–5 секунд, ровно 1 раунд диалога, ответ из подтверждённых данных
```

## 7. Что НЕ стоит делать

- **Fine-tune модели классификатора на 200 примерах.** Шум, переобучение,
  привязка к версии модели. Лучше промпт + few-shot.
- **Делать классификатор «многоступенчатым» внутри LLM.** Chain-of-thought
  в JSON-ответе → длиннее latency и больше брака парсинга. Каскад логики
  лучше держать снаружи (как в §3.2).
- **Заводить отдельную «маленькую и быструю» модель только для классификации.**
  На 70–120 документах разница в стоимости с llama-3.3-70b не оправдает
  поддержку второй интеграции.
- **Сразу включать probe retrieval в hot path без feature-flag.** Сначала
  shadow-mode: logging обоих результатов (legacy и new), сравнение, потом
  переключение.
